# AX58100 Boot EEPROM Emulation

This application already supports runtime EEPROM handling through SOES and the
local EEPROM backend in `src/eep_backend.c`. Boot-time EEPROM emulation is a
different path: the AX58100 reads its hardware configuration over its dedicated
I2C master pins during power-on or reset, before the PDI SPI interface is in
normal use.

## Required AX58100 Signals

From the AX58100 datasheet:

- `SCL`: I2C serial clock generated by the AX58100 I2C master.
- `SDA`: I2C serial data driven by the AX58100 I2C master.
- `PDI_EMU`: bootstrap/configuration pin related to PDI emulation mode.
- `EEP_DONE`: status output that indicates the EEPROM image was loaded.
- `RSTn/RSTO`: reset path. The MCU already controls ESC reset in
  `lib/soes/hal/ax58100/rst.c`.

The ESC configuration area at EEPROM offset `0x00..0x0F` is automatically read
by AX58100 after power-on or reset. That means boot emulation must be active
before the ESC is released from reset.

## Proposed MCU Pin Reservation

The current scaffold claims all four boot-interface pins in firmware:

- `PB10` -> `I2C2_SCL`  -> connect to AX58100 `SCL`
- `PB11` -> `I2C2_SDA`  -> connect to AX58100 `SDA`
- `PB9`  -> GPIO output -> drives AX58100 `PDI_EMU`
- `PC5`  -> GPIO input  -> reads AX58100 `EEP_DONE`

Notes:

- `PB10/PB11` avoid the already occupied `PA4..PA7` SPI1 ESC PDI pins.
- `PH0/PH1` stay reserved for a future external crystal and are not candidates
   for repurposing.
- `PB6..PB8` are already consumed by temporary GPIO inputs, so `I2C1` is a bad
  fit without remapping the IO pool.
- `PC2` remains the ESC reset pin handled by the existing reset HAL.
- `SCL` and `SDA` need external pull-up resistors because the AX58100 exposes
  them as tri-stateable I2C master lines.

## Expected EEPROM Model

The AX58100 does not hardcode a single commercial EEPROM part number. Instead,
it supports two addressing models selected by the `EEP_SIZE` bootstrap pin:

- `EEP_SIZE = 0`: `1 Kbit .. 16 Kbit` devices, with control byte
   `1010 A10 A9 A8 R/W` and one address byte. This is `24C16`-like behavior and
   requires multiple slave addresses (`0x50 .. 0x57`) for a full `16 Kbit`
   device.
- `EEP_SIZE = 1`: `32 Kbit .. 4 Mbit` devices, with control byte
   `1010 A18 A17 A16 R/W` and two address bytes. For a `32 Kbit` device this is
   effectively `24C32`-like behavior with base slave address `0x50`.

The generated `eeprom.bin` currently has `2048` bytes (`16 Kbit`). Even so, the
firmware intentionally emulates the `32 Kbit .. 4 Mbit` family because the STM32
`I2C2` hardware slave can cleanly expose one slave address with two address
bytes, while the `16 Kbit` family would need the `0x50 .. 0x57` multi-address
pattern. In practice that means the board bootstrap for `EEP_SIZE` should select
the `32 Kbit .. 4 Mbit` class and the emulated memory should be treated as a
`24C32`-style device with unused upper space returning `0xFF`.

Recommended choice for a new PCB:

- Use `LED_RUN / EEP_SIZE = 1` at reset.
- Design the boot EEPROM path around a `24C32`-like device model.
- Keep the current single-address `I2C2` slave implementation.

## Boot Sequence

1. MCU starts and configures the ESC reset pin as asserted.
2. MCU initializes the EEPROM image source from `src/eep_backend.c`.
3. MCU enables an I2C slave peripheral that behaves like the selected EEPROM
   type and size expected by AX58100.
4. MCU drives `PDI_EMU` on `PB9`.
5. MCU releases AX58100 reset.
6. AX58100 reads the boot EEPROM image through `SCL/SDA`.
7. MCU waits for `EEP_DONE` on `PC5` to assert or times out.
8. After `EEP_DONE`, normal SPI PDI startup can proceed and the existing SOES
   runtime EEPROM path remains available.

## Firmware Work Remaining

The current codebase now contains an initial boot-time I2C EEPROM scaffold in
`src/boot_eeprom_emu.c`. The remaining work is:

1. Validate the `I2C2` slave timing and protocol on real hardware against the
   AX58100 boot loader.
2. Validate that the board bootstrap for `EEP_SIZE` selects the `32 Kbit ..
   4 Mbit` EEPROM family expected by the current firmware.
3. If the hardware keeps `EEP_SIZE = 0`, replace the current single-address
   slave with a `24C16`-style multi-address emulation (`0x50 .. 0x57`).
4. Gate SPI/PDI initialization until `EEP_DONE` is observed or a boot timeout
   expires.
5. Decide whether runtime writes should also update the boot-time shadow used by
   the I2C slave without requiring a reboot.

## Relationship With Runtime SOES EEPROM

Boot EEPROM emulation and SOES runtime EEPROM handling are complementary:

- Boot path: MCU emulates the physical I2C EEPROM that AX58100 reads at reset.
- Runtime path: SOES handles `READ`, `WRITE`, and `RELOAD` requests through the
  ESC EEPROM registers using the backend implemented in `src/eep_backend.c`.

The same EEPROM image should back both paths so boot and runtime stay aligned.
